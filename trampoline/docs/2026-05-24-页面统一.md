# 2026-05-24 多页面 UI 统一与训练记录保存说明

## 任务目标

本轮工作把实时视频页、训练看板和档案页统一到当前视频分析页的视觉风格中，避免产品入口之间出现两套完全不同的界面语言。

目标分为三部分：

- `/` 实时视频页：在视频分析页结构基础上，重点替换左侧视频画面为实时视频流控制区；真实相机流和实时推理暂不接入。
- `/dashboard` 训练看板：接入当前已经完成的视频分析结果，支持保存训练记录，并区分离线视频与实时视频来源。
- `/profile` 档案页：不再做旧占位页，而是基于保存后的训练记录生成训练画像。

## 方案选择

现有 `/video_analysis` 已经完成主视觉迁移，包含：

- 顶部深蓝 `topbar`；
- `mode-tabs` 页面切换；
- `panel` 卡片；
- DETHP 评分、落点图、动作序列、AI 分析等裁判台式布局。

因此本轮没有重新设计一套 UI，而是让其他页面复用这套语言：

- 三个模板继续保留原路由；
- 模板引入 `video_analysis.css`；
- 新增 `static/css/trampoline_pages.css` 承接非视频分析页的局部布局；
- 不继续使用旧的 `dashboard.css` / `profile.css` 作为主样式。

这样做的好处是：主视觉只维护一套，后续如果调整品牌色、面板边框、标题样式，不会出现每个页面各自漂移的问题。

## 实现结果

### 1. 实时视频页

`templates/index.html` 改为新的实时裁判页面：

- 顶部标题改为“蹦床AI裁判系统 · 实时视频页面”；
- 左侧主面板为“实时视频画面”；
- 等待上传区域改为“等待连接实时相机”；
- 控制按钮改为“启动相机 / 停止 / 切换到离线分析”；
- 底部显示训练来源为 `realtime_video`；
- 右侧评分、落点、腾空曲线、AI 分析区域先保留为实时预留状态。

注意：按钮当前是禁用状态，因为本轮不实现真实摄像头采集接口。这样可以让界面先统一，但不会误导用户以为实时流已经可用。

### 2. 训练看板

`templates/dashboard.html` 改为新看板：

- 显示已保存训练、累计跳次、最佳总分、主要动作；
- 显示离线视频 / 实时视频 / 全部记录筛选；
- 从当前已完成的视频分析中列出可保存项目；
- 保存后写入训练记录；
- 使用动作分布条和来源构成条替代旧占位图。

新增接口：

```http
POST /api/training/sessions
GET /api/training/sessions?source=offline_video|realtime_video|all
```

保存的数据会写入：

```text
uploads/training_sessions.json
```

记录字段包含：

- `id`
- `source`
- `created_at`
- `video_id`
- `total_jumps`
- `effective_jumps`
- `action_distribution`
- `score`
- `score_total`
- `duration`
- `selected_jump_numbers`

其中 `source` 是这次数据隔离的关键字段：

- `offline_video`：离线视频分析保存的数据；
- `realtime_video`：后续实时视频流保存的数据。

### 3. 档案页

`templates/profile.html` 改为训练档案概览：

- 使用同样的顶部导航和深蓝品牌栏；
- 展示运动员档案头部；
- 展示训练次数、累计跳次、最佳总分、主要动作；
- 展示训练侧重点；
- 展示最近 5 条保存训练。

本轮没有做账号系统或档案编辑，因为当前项目还没有用户体系。档案页先从保存训练中生成只读画像，更符合当前代码基础。

## 后端改动

`app.py` 新增训练记录相关辅助函数：

- `_training_sessions_path()`
- `_load_training_sessions()`
- `_save_training_sessions()`
- `_analysis_to_training_session()`
- `_training_summary()`
- `_filter_training_sessions()`

核心思路是：

1. 从 `video_analyses` 中找到已完成的离线视频分析；
2. 调用已有评分逻辑 `_score_for_status()` 获取 DETHP 评分；
3. 把跳次、动作分布、评分、来源等字段整理成 session；
4. 写入 JSON 文件；
5. 看板和档案页都消费同一份 session 数据。

## 问题修正过程

### 旧页面风格不一致

实时页、看板和档案页原来仍使用旧 `container/header` 页面结构，与视频分析页割裂明显。

修正方式：

- 删除旧模板主体；
- 统一换成 `app-shell/topbar/panel`；
- 保留原路由，避免外部入口失效。

### 看板没有真实数据

旧看板只有占位摘要和静态图表。

修正方式：

- 从 `video_analyses` 找已完成分析；
- 新增保存 API；
- 保存后的记录用于看板统计；
- 使用 `source` 区分离线和实时来源。

### 保存功能不能只放内存

如果只把保存结果存在 Python 进程内，刷新页面可以看到，但服务重启后会丢失，不符合“保存”的直觉。

修正方式：

- 使用 `uploads/training_sessions.json` 做轻量持久化；
- 不新增数据库依赖；
- 保存同一个 `source + video_id` 时覆盖更新，避免重复堆积。

## 学习要点

如果你有 MCU C 背景，可以把这次改动理解成“显示界面、通信协议、数据存储”三层分离。

### 1. 模板像显示屏布局

HTML 模板主要决定界面上有什么区域。比如实时页左侧视频画面、看板统计卡片、档案概览卡片，都属于“屏幕上显示哪些控件”。

不要把复杂数据计算写进模板。模板应该尽量只做：

- 显示字段；
- 循环列表；
- 放按钮；
- 提供容器。

### 2. CSS 像统一外观参数

`video_analysis.css` 是主视觉参数，类似一套显示屏 UI 规范。

`trampoline_pages.css` 只补充其他页面自己的布局，不去重写所有基础样式。这样可以避免：

- 一个按钮在视频分析页是蓝色，在看板页变成另一套样式；
- 每个页面都维护自己的边框、阴影和标题样式；
- 后续改一次主风格，要改很多文件。

### 3. Flask API 像通信协议

`POST /api/training/sessions` 就像 MCU 和上位机之间定义的一条命令：

- 输入：`video_id` 和 `source`；
- 校验：视频是否存在、是否完成分析、来源是否合法；
- 输出：保存后的训练记录。

接口一旦稳定，前端只需要按协议调用，不需要知道后端内部怎么计算动作分布和评分。

### 4. JSON 文件像简易 EEPROM

本轮没有引入数据库，而是用 JSON 文件保存训练记录。

它的优点是：

- 简单；
- 可读；
- 适合当前小规模本地项目；
- 不增加部署复杂度。

它的限制是：

- 并发写入能力弱；
- 不适合大量历史记录；
- 后续如果有用户登录、多设备同步，就应该换 SQLite 或正式数据库。

## 后续建议

1. 实时流接入时，不要直接复用离线视频上传接口。建议新增独立实时流状态接口，再把最终训练摘要保存为 `source=realtime_video`。
2. 看板可以继续扩展趋势图，例如按日期统计训练次数、平均 H 分、平均 T 分和最佳总分。
3. 档案页后续可以加入训练目标、器材配置、常用床面标定参数，但应等真实用户体系明确后再做可编辑表单。
4. 如果训练记录开始增多，应把 `uploads/training_sessions.json` 迁移到 SQLite，并给 session 增加版本字段。
5. 后续如果要做“从视频分析页一键保存”，可以复用本轮新增的 `POST /api/training/sessions`，不用再新增一套保存逻辑。
