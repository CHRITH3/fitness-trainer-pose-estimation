# 2026-05-23 视频页 UI 迁移与问题修正说明

## 任务背景

本轮工作围绕 `/video_analysis` 页面展开，目标是把当前项目中的蹦床视频分析界面迁移到 `/UI_CHANGE` 目录中整理好的目标样式，并根据实际联调中暴露的问题继续修正交互和信息结构。

这次不是一次单纯的“换皮”：

- 页面视觉结构参考了 `/UI_CHANGE` 中的目标 HTML 页面和截图。
- 迁移方案参考了 `/UI_CHANGE/MIGRATION_GUIDE.md`。
- 实际实现仍然要保留当前项目已有的 Flask API、上传流程、床面标定流程、轮询流程、SSE AI 分析流程和报告下载能力。

因此，本轮工作的核心约束是：

1. **视觉结构向目标 UI 靠拢**；
2. **业务流程不能被静态示例页面替换**；
3. **旧 JS 依赖的 DOM ID 不能随意删除**；
4. **AI 输出不能因为文本很长而撑坏整个页面布局**。

## 总体目标

最终页面需要形成一个接近目标 UI 的三列工作台：

- 左侧：离线视频画面、上传、本地视频播放、标定 overlay 和分析进度。
- 中间：落点可视化、腾空时间曲线、下方工作流区。
- 右侧：实时评分、AI 分析建议和报告下载入口。

同时，下方工作流区需要从单一标定块调整为两个选项卡：

- **标定交互**：负责床面角点标定、重新标定、标定状态和标定结果显示。
- **动作序列**：负责展示识别出的逐跳数据，并整合动作分布、过渡跳、处理耗时等报告摘要。

AI 分析区需要满足两件事：

- 生成完成后的内容不能把“离线视频画面”“腾空时间曲线”“动作序列”等栏位继续向下拉长。
- 点击“下载报告”时，报告中要包含 AI 分析结果。

## 问题来源与修正过程

### 1. 删除不应该保留的旧卡片

迁移初期仍保留了旧页面中的几个信息卡片：

- 实时统计
- 过程反馈
- 分析报告

这些卡片在旧版页面中承担过摘要展示和调试反馈功能，但目标 UI 中已经重新组织了信息层级：

- “实时统计”的一部分信息被右上角“实时评分”和底部状态条吸收。
- “过程反馈”不再作为主视觉卡片展示，只保留必要的内部日志和隐藏兼容节点。
- “分析报告”不再独立成卡，而是并入“动作序列”的逐跳数据和摘要统计中。

修正时没有简单把所有相关 DOM 都删除，因为 `static/js/video_analysis.js` 仍然会读取若干旧 ID。做法是：

- 删除用户可见的旧卡片；
- 保留必要的隐藏兼容节点；
- 让旧 JS 查询不会返回 `null`；
- 把真实可见信息迁移到新布局中。

这类处理的重点是区分：

- **产品上不应该再显示的东西**；
- **代码运行仍然需要的 DOM 合约**。

### 2. 修复 AI 分析无法正常启动

AI 分析无法启动的根本原因不是模型侧，而是 UI 迁移后按钮、报告区和完成态显示逻辑发生了位置变化。

旧页面里，“分析报告”和“AI 分析”是相邻区域；迁移后独立报告卡被删除，如果 JS 仍然围绕旧报告区切换显示状态，就容易出现：

- AI 按钮没有在分析完成后启用；
- AI 区域被旧的隐藏逻辑影响；
- 用户能看到页面完成了，但无法触发 `/api/video/llm_analysis/<video_id>`。

修正思路是把 AI 分析区确立为新的主入口：

- `llm-section` 保持为可见 AI 面板的核心容器。
- `llm-btn` 仍负责启动 SSE AI 分析。
- 分析完成后，`handleAnalysisComplete` 负责启用 AI 按钮。
- 报告下载按钮移动到 AI 分析区，但不再阻断 AI 按钮状态。

这样页面语义变成：

> 视频分析完成以后，动作序列负责本地结构化结果，AI 分析负责生成解释性建议，报告下载负责汇总两者。

### 3. 补齐标定交互和动作序列切换

目标 HTML 页面已经实现了“标定交互 / 动作序列”的切换，但项目页面一开始只迁移了视觉框架，没有完整恢复这个交互。

修正后，工作流区拆成两个 tab：

- `show-calibration`：切到标定交互。
- `show-sequence`：切到动作序列。
- `corner-marking-step`：标定交互内容容器。
- `jump-list-step`：动作序列内容容器。

同时，“重新标定”相关操作被放回标定交互页签，而不是散落在页面底部或视频区外部。

这样处理的原因是：

- 标定是一组前置交互，不应该和动作结果混在同一层。
- 重新标定属于标定流程的二次进入，也应该和当前标定状态、标定点位结果放在一起。
- 动作序列只关注“分析后结果”，避免用户在结果区误以为还可以标点。

### 4. 修正右上角布局并加入腾空时间曲线

用户指出右上角布局和目标 UI 仍不一致：目标截图中右上角是“实时评分”，中间区域包含“落点可视化”和“腾空时间曲线”。

修正后页面布局改为：

- 中上：落点可视化。
- 右上：实时评分。
- 中下：腾空时间曲线。
- 右侧下方：AI 分析卡片。

新增 `flight-panel` 和 `flight-chart`，由前端根据分析结果绘制腾空时间曲线：

- 横轴表示跳次。
- 纵轴表示腾空时间。
- 当前跳或最新结果可以参与曲线刷新。
- 没有足够数据时显示空状态。

这一步的关键是不能只在 HTML 里加一个空卡片，还要让 `video_analysis.js` 在轮询状态和分析完成后都能更新图表。

### 5. 避免 AI 长文本撑高整个页面

使用 `deepseek-v4-pro` 完成 AI 分析后，输出内容较长，导致 AI 卡片高度增加，并进一步把“离线视频画面”“腾空时间曲线”“动作序列”等区域整体拉长。

这个问题本质上是布局容器没有设置明确的承载边界：长文本被当成普通文档流内容，浏览器就会自然把父容器撑开。

修正方案是把 AI 结果从“长文平铺”改成“固定高度面板 + 分段切换”：

- `整体表现`
- `主要问题`
- `逐跳点评`
- `改进建议`

这四个按钮对应 `llmSections` 中的四段内容，点击按钮只替换 `llm-active-panel` 内部内容，不改变页面整体网格高度。

其中，“逐跳点评”又做了进一步压缩：

- 第一层只显示“第几跳”和动作名称。
- 用户 hover 或键盘 focus 到某一跳时，再显示该跳详细点评浮层。

这样页面不需要一次展开十几跳的详细文字，也不会因为模型输出很长而破坏目标 UI 的布局。

### 6. 报告下载加入 AI 内容

旧的下载报告只包含本地结构化结果，例如：

- 总跳次
- 过渡跳
- 动作分布
- 处理耗时
- 每跳明细
- 过程日志

修正后，`download-report-btn` 会额外读取当前缓存的 AI 内容：

- `llmSections`
- `llmFullText`
- `llmSource`

如果用户已经完成 AI 分析，下载文本报告时会追加：

- AI 分析来源
- 四个分段的 AI 内容
- AI 原文

这样报告不再只是“算法结果清单”，而是同时包含结构化数据和 AI 解释建议。

### 7. 解释端口 5000 被占用

联调时出现过：

```text
Address already in use
Port 5000 is in use by another program.
```

原因是前一次 Flask 服务仍在运行，或者开发验证时启动的本地服务没有及时退出。Flask 默认使用 `127.0.0.1:5000`，同一台机器上同一时间只能有一个进程绑定这个端口。

处理方式是：

- 查找仍在运行的 Flask 进程；
- 停止旧进程；
- 或者临时换一个端口启动；
- 完成冒烟验证后及时停止服务。

这个问题和 UI 代码本身无关，但会影响验证体验，所以也纳入本轮记录。

## 最终页面结构

本轮之后，页面可以按“主工作流 + 辅助分析”的方式理解。

### 主视频区

主视频区保留上传、播放、标定 overlay、分析进度和基础状态提示。

关键点是：

- 标定 overlay 仍复用 `analysis-canvas`。
- 用户需要先进入标定流程，再点击视频画面上的床面角点。
- 标定 canvas 只在标定激活时接管交互，不持续遮挡视频控制。

### 中间分析区

中间区负责高频视觉反馈：

- 落点可视化：展示床面落点分布。
- 腾空时间曲线：展示每跳腾空变化。

这两个区域都属于“看趋势”的信息，而不是详细解释，因此适合放在视频旁边。

### 右侧分析区

右侧上方放实时评分，右侧下方放 AI 分析。

实时评分用于快速判断当前结果，AI 分析用于在完成处理后生成文字建议。下载报告也放在 AI 区域，因为最终报告现在包含 AI 内容。

### 下方工作流区

下方工作流区是本轮最重要的结构调整之一：

- 标定交互：负责输入床面标定数据。
- 动作序列：负责输出识别后的逐跳结构化数据。

这种拆分避免了“输入动作”和“输出结果”混在一张卡片里。

## 关键实现落点

### `templates/video_analysis.html`

这个文件负责页面结构：

- 引入新的三列 dashboard 布局。
- 新增 `flight-panel` 和 `flight-chart`。
- 新增工作流 tab：`show-calibration` / `show-sequence`。
- 将重新标定、标定状态和标定结果放回标定交互区域。
- 将动作序列、动作分布、处理耗时等摘要放到动作序列区域。
- 将 AI 分析卡片放到右侧，并提供四个 AI 分段按钮。
- 保留隐藏兼容 DOM，避免旧 JS 查询 ID 时失败。

### `static/css/video_analysis.css`

这个文件负责把目标 UI 视觉落地：

- 使用 grid 控制视频区、中间区、右侧区和下方工作流的布局。
- 控制 `flight-panel`、`score-panel`、`ai-panel` 等卡片位置。
- 为 AI 分析结果设置固定承载区域和内部滚动。
- 为 `llm-jump-detail-popover` 设置 hover / focus 浮层。
- 保证标定激活时 `analysis-canvas` 才可交互。

本轮 CSS 的重点不是颜色，而是三个布局纪律：

1. 长文本必须有自己的滚动容器。
2. 卡片高度不能被模型输出无限撑开。
3. 交互态要通过 class 明确表达，例如 `calibration-active`。

### `static/js/video_analysis.js`

这个文件负责页面状态和数据更新：

- `setWorkflowTab` 控制标定交互和动作序列切换。
- `buildJumpSummary` 计算动作分布、过渡跳和处理耗时等摘要。
- `renderFlightChart` 绘制腾空时间曲线。
- `setLlmSections` 缓存 AI 分段结果。
- `renderLlmSection` 根据 tab 切换 AI 当前显示段落。
- `renderJumpDetailPanel` 将逐跳点评压缩为“序号 + 动作 + 浮层详情”。
- `appendAiReportText` 将 AI 结果加入下载报告。

本轮 JS 的重点是把“页面上显示什么”从“数据如何产生”中分离出来。后端仍然负责分析，前端只负责把结果组织成合适的信息层级。

### `tests/test_trampoline_frontend_contract.py`

这个测试文件保护前端 DOM 合约：

- 确认旧 JS 仍需要的关键 ID 存在。
- 确认新增的工作流 tab 存在。
- 确认腾空时间曲线卡片存在。
- 确认 AI 分段 tab、固定面板和逐跳浮层相关结构存在。
- 防止旧的 `report-details-toggle` 逻辑回流。

这类测试不负责判断页面“好不好看”，它负责防止以后改 HTML 时把 JS 依赖的节点删掉。

## 为什么不能直接复制 `/UI_CHANGE` 的页面

`/UI_CHANGE` 中的页面更像一个目标样式和交互参考，它可以告诉我们：

- 页面应该长什么样；
- 哪些区域应该在什么位置；
- 哪些按钮和标签页应该出现；
- 用户期望的操作路径是什么。

但它不能直接替换当前项目页面，因为当前项目已经有真实业务链路：

- Flask 上传接口；
- 视频状态轮询接口；
- 床面标定控制器；
- 蹦床分析 subprocess；
- 处理后视频回放；
- LLM SSE 流式输出；
- 测试保护的 DOM ID 合约。

直接复制静态 HTML 的风险是：

- 样式看起来对了，但按钮没有真实功能；
- 真实 JS 找不到原来的 DOM ID；
- 标定和 AI 分析被静态示例逻辑覆盖；
- 回归测试无法通过。

因此本轮采用的是“参考视觉，移植结构，保留业务”的方式。

## 如何学习到能独立完成这次 UI 更改

如果想以后自己独立完成类似改版，建议不要从“先学 CSS 美化”开始，而是按下面顺序训练。

### 1. 先画页面状态机

这类页面不是静态展示页，它有明确状态：

- 初始待上传
- 已上传待标定
- 标定中
- 标定完成可分析
- 分析中
- 分析完成
- AI 分析中
- AI 分析完成

每个状态对应哪些按钮可点、哪些面板显示、哪些数据更新，都应该先列出来。

如果有 MCU C 背景，可以把它理解成一个前端状态机：

- 上传按钮像一个外部输入；
- 分析轮询像定时器；
- SSE AI 输出像串口流；
- DOM 更新像刷新显示屏缓存。

先把状态机想清楚，后面写 JS 才不会变成到处补 if。

### 2. 学会找 DOM 合约

前端 JS 经常通过下面这种方式找页面节点：

```js
document.getElementById('llm-btn')
```

这意味着 `llm-btn` 不是随便一个名字，而是 HTML 和 JS 之间的合约。删除或改名以后，JS 可能就会失效。

做 UI 迁移前，应该先用搜索工具找出：

- JS 读取了哪些 ID；
- CSS 依赖了哪些 class；
- 测试保护了哪些结构；
- 后端模板是否生成了特殊数据。

在本项目中，可以优先用：

```bash
rg "getElementById|querySelector|id=|class=" templates static/js static/css tests
```

这一步相当于 MCU 里检查外设寄存器映射：不能因为重新画了面板，就把代码还在读写的地址改没了。

### 3. 把页面拆成“输入区”和“输出区”

这次最容易混乱的地方，是床面标定和动作结果都在同一个页面。

正确拆法是：

- 标定交互是输入；
- 动作序列是输出；
- AI 分析是二次解释；
- 下载报告是汇总导出。

只要这样分清楚，按钮应该放哪里就会自然很多：

- “重新标定”属于输入区，所以放到标定交互。
- “每跳详细数据”属于输出区，所以放到动作序列。
- “下载报告”包含 AI 内容，所以放到 AI 分析区。

### 4. 学会用 CSS Grid 对照截图落位

目标截图不是让人逐像素复刻，而是提供信息布局：

- 哪个区域最重要；
- 哪个区域应该在首屏；
- 哪些卡片应该上下对应；
- 哪些区域不能互相挤压。

实现时应该先把页面当成网格：

- 视频区占左侧大块；
- 落点和曲线在中间；
- 评分和 AI 在右侧；
- 工作流跨下方。

然后再处理边距、颜色、字号。

如果先调颜色，很容易做出“看起来像，但结构不对”的页面。

### 5. 长内容一定要设计承载方式

AI 输出、日志、逐跳明细这类内容都可能很长。长内容不能简单放进普通卡片，否则会把父容器撑开。

常见处理方式有：

- 固定高度 + 内部滚动；
- tab 分段；
- 折叠详情；
- hover / focus 浮层；
- 摘要优先，详情按需展开。

本轮采用的是：

- AI 四段 tab；
- 当前段固定面板；
- 逐跳点评只显示序号和动作；
- 详细点评通过浮层查看。

这就是前端里的“限流”和“缓冲区”思维：数据可以很多，但显示通道要有边界。

### 6. 改完 UI 必须做契约测试

只靠肉眼看页面是不够的，因为很多问题要到点击按钮或异步状态切换时才出现。

本轮使用的验证方式包括：

- Python route / API contract tests；
- 前端 DOM contract tests；
- Node UI helper tests；
- 本地 Flask 冒烟验证；
- `git diff --check` 检查格式问题。

建议形成习惯：

1. 小改 HTML 后跑前端 contract test。
2. 改 JS 状态逻辑后跑 Node helper test。
3. 改 Flask route 或 API 后跑对应 pytest。
4. 最后再浏览器冒烟点一遍主流程。

## 当前仍需注意的点

### 1. D / E / T 评分仍偏展示层

右上角“实时评分”目前主要是目标 UI 结构中的展示卡片。后续如果要把 D 分、E 分、T 分做成严格的规则评分，需要进一步定义：

- 每个分数来自哪些算法字段；
- 扣分规则如何计算；
- 空中姿态、落点偏差、腾空时间波动如何映射到分值；
- 是否需要后端返回更稳定的评分结构。

### 2. AI 文本解析依赖标题结构

AI 分段展示依赖模型输出中的语义标题，例如“整体表现”“主要问题”“逐跳点评”“改进建议”。

如果未来更换提示词或模型，最好让后端 LLM 服务输出更稳定的结构化字段，而不是完全依赖前端从长文本中切段。

更稳的方向是：

- 后端同时返回 `sections` JSON；
- 前端只负责渲染；
- 原始文本作为备用显示。

### 3. 报告仍是纯文本

当前下载报告仍是 `.txt` 文本文件。它简单、稳定、容易调试，但如果要用于正式交付，可以考虑：

- HTML 报告；
- PDF 报告；
- Word 报告；
- 带截图、落点图、曲线图的图文报告。

这些都不应该在本轮 UI 修正里强行加入，否则会扩大范围。

## 后续建议

### 1. 增加浏览器截图回归

当前 contract test 能保护 DOM 结构，但不能判断视觉位置是否和目标截图一致。后续可以补一个 Playwright 冒烟测试：

- 打开 `/video_analysis`；
- 截取桌面尺寸页面；
- 检查关键卡片是否在预期区域；
- 检查 AI 长文本不会撑高页面。

### 2. 将 AI 渲染逻辑继续抽小

`static/js/video_analysis.js` 目前承担较多职责：

- 上传；
- 标定；
- 轮询；
- 图表；
- 动作序列；
- AI 分析；
- 报告下载。

如果后续 AI 面板继续复杂化，可以考虑抽出：

- `static/js/trampoline_llm_panel.js`
- 或者 `static/js/video_analysis_report.js`

但当前阶段不急着拆，先保持行为稳定更重要。

### 3. 为 AI 报告补结构化测试

建议后续增加一个前端测试，专门验证：

- AI 四段内容能被缓存；
- tab 切换能显示正确段落；
- 逐跳点评能折叠为序号和动作；
- 下载报告包含 AI 内容。

这样以后改提示词或改报告格式时，不容易漏掉导出逻辑。

### 4. 明确长期 UI 规范后再更新 AGENTS.md

本轮没有改变运行命令、核心模块或技术栈，因此不必立刻更新 `AGENTS.md`。

但如果这个目标 UI 会成为后续所有蹦床页面的长期规范，可以考虑在 `AGENTS.md` 里补充：

- `/video_analysis` 使用目标工作台布局；
- 标定输入和动作输出分 tab；
- 长 AI 内容必须使用固定面板或折叠展示；
- 不再恢复旧的实时统计、过程反馈、独立分析报告卡片。

这样后续任务就不会把旧卡片误加回来。

## 总结

这次 UI 迁移的重点不是“把页面改得像截图”，而是把目标 UI 转换成当前项目能真实运行的产品页面。

最终实现遵循了三条主线：

1. **视觉对齐目标页面**：三列工作台、右上评分、中部落点和曲线、右侧 AI。
2. **业务流程保持可用**：上传、标定、分析、AI SSE、报告下载都继续走当前项目逻辑。
3. **长内容受控展示**：AI 结果通过四段 tab 和逐跳浮层避免撑坏页面。

后续如果继续迭代，优先做视觉截图回归、AI 输出结构化和正式报告格式，而不是继续堆更多卡片。
