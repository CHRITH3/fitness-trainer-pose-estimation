# 蹦床关键帧标定：从“只标首帧”到“按时间锚点修正”

## 任务目标

这次工作的目标是：**在不暂停后台分析、不改跳跃分割逻辑、不增加依赖的前提下，把床面标定从“只依赖首帧”升级为“支持多个关键帧”。**

如果把 2026-04-17 的版本看成“先把床面坐标链路打通”，那么这次就是在解决一个更实际的问题：

> 视频一旦变长，或者拍摄过程中有轻微移动，首帧标定对后续整段视频的约束会越来越弱。

## 原始问题是什么

首帧标定适合做 MVP，但它有天然局限：

1. **长视频容易累积漂移**
   - 即使每一帧都在追踪，累计误差还是会慢慢变大。
2. **手持/轻微摇晃视频更容易偏**
   - 只靠“从第一帧推到最后一帧”的思路，容错性不够。
3. **用户其实能提供更强的人类先验**
   - 用户知道哪些时间点是清楚的、适合重新标定的。

所以这次不是推翻自动跟踪，而是给自动跟踪加入**人工关键帧锚点**。

## 为什么方案是“多关键帧 + 平滑过渡”

这里有几种可能路线：

- 完全相信自动跟踪
- 每次漂移就重做整段分析
- 允许用户补几个关键帧，让系统在这些锚点之间平滑过渡

最终选第三种，原因是它最符合现有工程结构：

- 后端已有 `BedTracker`
- 前端已有视频预览能力
- API 已有 trampoline start 提交流程

也就是说，这次不是另起一套“重标定系统”，而是在原有链路上补一个更实用的时间维度。

## 关键思路：把关键帧看成“时间锚点”

你可以把每个关键帧理解成一条记录：

- 这组四角属于哪一帧：`frame_index`
- 这组四角大概对应多少秒：`time_s`
- 这组四角具体是多少像素坐标：`corners_px`

然后 `BedTracker` 在运行时按帧号选择“当前更接近哪个人工锚点”，并在相邻关键帧之间做平滑过渡。

这比“首帧永远有效”更贴近真实拍摄情况。

## 这次具体改了什么

### 1. 前端：支持多关键帧标定

用户在待标定阶段可以：

- 预览视频
- 暂停视频
- 拖动到某一帧
- 添加当前帧标定
- 保存多个关键帧

这样，用户不需要放弃原有上传流程，只是在分析前多做一步“按时间点补锚”。

### 2. API：`/api/video/trampoline/start` 兼容两种输入

新版 start 接口支持：

- 新格式：`calibrations[]`
- 旧格式：`corners`

这意味着旧调用方不会立刻失效。旧的首帧模式会被自动规范化成：

- `frame_index = 0`
- 一条单关键帧记录

### 3. sidecar：从 v1 进化到 v2

sidecar 不再只保存首帧四角，而是支持完整的 `calibrations[]` 列表。

兼容策略是：

- 旧 schema v1 继续可读
- 新 schema v2 能表达多个关键帧

这是一种典型的“加法式升级”：旧数据不废，新能力继续长出来。

### 4. `BedTracker`：支持关键帧人工锚点与平滑过渡

`BedTracker` 增加了：

- 关键帧归一化与校验逻辑
- 从 sidecar 读取 `calibrations[]`
- `BED_KEYFRAME_TRANSITION_FRAMES = 20` 这样的过渡窗口配置
- 在关键帧附近更平滑地切换到人工四角

这里的重点不是“读到多个关键帧”，而是“切换不能生硬”。

### 5. marker line 与 minimap 一起增强

这次同时补上了两个可视化能力：

- **marker line 最佳努力高亮**
- **自适应缩放的落点 minimap**

它们的作用是让教练和开发者更容易判断：

- 床面跟踪有没有贴住真实边界
- 落点图在不同分辨率下是不是还能看清楚

## 兼容性为什么值得单独记录

兼容性不是“顺手做一下”，而是这次方案能否安全上线的关键。

### 旧请求如何兼容

旧版只有 `corners`。新版会把它规范化成：

- `frame_index = 0`
- 单个 calibration

所以旧调用方不需要立刻修改。

### 旧 sidecar 如何兼容

解析逻辑同时支持：

- schema v1
- schema v2

因此你不必为了测试关键帧功能，把旧数据全部重录一遍。

### 旧落点 payload 为什么不受影响

这次新增的 marker-line 信息，只挂在诊断字段里，不改 `landing` 的主语义。

这说明这次迭代属于：

> 在原有主数据契约不破坏的情况下，增加更细的时间锚点与诊断信息。

## 这次能学到什么

### 1. `frame_index` 很像 MCU 里的“时间基准点”

如果你做过单片机开发，可以把关键帧理解成“按时间轴写进去的一组校准参数”。

- 在固件里，你可能按温度点或档位保存一组校准值
- 在这里，系统按 `frame_index` 保存一组床角坐标

运行时再根据当前帧号，决定该使用哪组参数，或者在两组参数之间过渡。

### 2. “规范化输入”是做兼容升级的关键技巧

`validate_calibrations()` 先把用户输入统一变成标准记录，然后 `BedTracker` 再使用它。

这一步非常重要，因为它把系统拆成两层：

- 第一层：清洗和校验输入
- 第二层：真正消费输入做业务逻辑

对 C 背景的人来说，这有点像：

- 先把串口收到的数据包校验和解包
- 再交给主状态机处理

如果这两步混在一起，系统会很难维护。

### 3. 平滑过渡比“立刻切换”更像真实系统

`BED_KEYFRAME_TRANSITION_FRAMES` 的意义，就是不要在某一帧突然把床面四角从 A 跳到 B。

在 UI 或视频系统里，这种突变通常会让结果看起来抖动、不可信。平滑过渡虽然实现稍复杂，但更符合用户感受。

## 验证

本任务要求的自动化验证命令包括：

```bash
node tests/test_trampoline_calibration_geometry.mjs
pytest tests/test_bed_tracker.py -v
pytest tests/test_trampoline_api.py -v
pytest tests/test_trampoline.py -v
```

这些测试分别在保护不同层次：

- `geometry`：前端点击坐标映射
- `bed_tracker`：关键帧与追踪逻辑
- `trampoline_api`：请求与 sidecar 契约
- `trampoline.py`：主分析逻辑回归

## 后续优化

如果下一轮继续做这条链路，优先级建议如下：

1. 给关键帧补标增加更直观的 UI 引导。
2. 为关键帧切换过程补更多真实视频样本验证。
3. 如果后续关键帧数量继续增长，可把时间轴与关键帧列表做得更直观。
4. 如果真实视频里仍出现局部漂移，可继续结合 marker line 和后续补标策略做增强。
5. 如果要继续教学化整理，后续可把 schema v1 / v2 的对照表补成单独小节，方便读者快速查阅。

这次工作的核心方法可以总结成一句话：

> 当首帧参数不足以约束整条时间轴时，不要急着推翻系统，先给它增加“按时间补锚”的能力。
