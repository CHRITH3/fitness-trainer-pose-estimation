# 实时接入说明

## 任务背景

本次任务是把 `/home/chris4/workspace/from_vm/YOLO_rec/get_pose_oak_rgbd.cpp` 的 OAK RGBD 实时视频、鼠标点击标定、深度滤波参数、落点记录等交互，接入当前项目的实时视频页面 `/`。

目标不是把 OpenCV 窗口“嵌进网页”，而是把 C++ 程序改造成一个本地实时服务，再让 Flask 页面作为上位机显示画面、发送控制命令。这样可以保留原来的实时计算链路，也能继续使用当前项目已经设计好的 Flask + HTML + CSS + JS 页面。

最终访问路径保持不变：

```text
浏览器访问： http://127.0.0.1:5000/
C++ 服务：   http://127.0.0.1:8081
```

## 本次选择的方案

参考 `YOLO_rec/docs/ChatGPT-YOLO实时视频集成方案.md` 中的讨论，方案大致有五类：

| 方案 | 核心思路 | 当前状态 |
|---|---|---|
| Flask MJPEG + HTTP 控制 | C++ 输出 JPEG，Flask 转发视频和控制命令 | 本次已实现其中的核心能力 |
| C++ 引擎 + Flask/WebSocket 桥接 | 视频、状态、控制统一走 WebSocket 或消息队列 | 后续正式增强方向 |
| C++ 自建 HTTP/WebSocket 服务 | C++ 自己提供 `/stream`、`/status`、`/click` 等接口 | 本次采用了这个结构，并让 Flask 做代理 |
| pybind11 动态库 | 把 C++ 封装成 Python 可调用库 | 暂不采用 |
| WebRTC/GStreamer | 专业低延迟视频传输 | 后续远程化再考虑 |

本次实际落地的是一个折中方案：

```text
OAK + YOLO C++ 实时程序
  ├── GET  /stream          MJPEG 实时主画面
  ├── GET  /status          FPS、检测人数、标定状态、落点数、滤波参数
  ├── POST /click           网页点击坐标
  ├── POST /filter_params   深度滤波参数
  └── POST /control         录制、清空、保存、显示开关等命令

Flask 项目
  ├── /                     原实时页面
  └── /api/realtime/*       代理到 C++ 服务

浏览器
  ├── <img> 显示 MJPEG
  ├── 点击图像完成床面四角标定
  ├── 滑条和下拉框调深度滤波
  └── 按钮控制落点记录和显示选项
```

这样做的好处是：C++ 仍然负责高频、重计算、硬件相关逻辑；Flask 仍然负责网页、页面路由、训练数据和后续 AI 分析。两个系统之间只通过清晰的 HTTP 接口交互。

新的服务模式是：

```bash

```

服务模式下新增了 `RealtimeBridge`。它负责：

- 在 `127.0.0.1:8081` 开 HTTP 服务。
- 保存最新一帧 JPEG。
- 保存最新状态 JSON。
- 接收网页发来的点击、滤波、控制命令。
- 用线程安全队列把命令交给主循环处理。

主循环没有被改成另一个全新流程，而是保留原来的 OAK 采集、YOLO 推理、深度计算、姿态绘制、落点检测逻辑，只在几个边界加了 Web 入口：

- 原来 `cv::imshow(kMainWindow, display)` 负责显示画面。
- 现在服务模式下改为 `cv::imencode(".jpg", display, ...)` 后发布到 `/stream`。
- 原来 `cv::setMouseCallback(..., OnDepthMouseCallback, &depth_region)` 接收 OpenCV 窗口鼠标。
- 现在服务模式下 `/click` 收到 `{x, y}` 后调用 `depth_region.OnMouse(cv::EVENT_LBUTTONDOWN, x, y, 0)`。
- 原来 `createTrackbar` 直接修改 `DepthUiState`。
- 现在网页滑条 POST 到 `/filter_params`，主循环调用 `ApplyFilterParams`、`ClampDepthUiState`、`MakeOakFilterConfig`、`oak_capture.UpdateFilterConfig`。
- 原来键盘 `r/c/s/k/t/i/+/-/[/]` 控制录制、落点、显示和参数。
- 现在网页按钮 POST 到 `/control`，主循环映射成同样的动作。

`app/depth_region.h` 增加了一些只读 getter：

- `GetRoiClickCount`
- `IsPlaneFitReady`
- `GetPlaneInlierCount`

这些 getter 让 `/status` 能把床面标定进度和状态暴露给网页。

const rect = video.getBoundingClientRect();

## 为什么这样拆

### C++ 是实时下位机

`get_pose_oak_rgbd.cpp` 做的是高频实时任务：

- OAK RGBD 采集。
- DepthAI 设备初始化。
- YOLO pose 推理。
- 深度图滤波。
- 3D 骨架和床面坐标变换。
- 落点检测。
- 画面叠加绘制。

这类逻辑像 MCU 或下位机程序，特点是状态连续、帧率敏感、硬件依赖强。如果把它塞进 Flask 进程，Python Web 服务就会同时承担硬件、推理、页面请求，调试和稳定性都会变差。

### Flask 是 Web 上位机

当前项目的强项是：

- 页面路由。
- 静态资源。
- 离线视频分析。
- 训练记录。
- 评分和 AI 分析。
- 用户档案 / 看板。

这些都属于上位机业务层。它不需要知道 OAK 内部怎么取帧，只需要知道“实时服务现在有什么状态”和“我要发送什么控制命令”。

### HTTP 接口是边界

这次最重要的工程边界是：

```text
C++ 对外只承诺接口，不承诺内部实现。
Flask 对前端只承诺 /api/realtime/*，不暴露 C++ 细节。
前端只绑定 Flask 接口，不直接依赖 C++ 端口。
```

这种边界能让后续演进更容易。例如以后把 MJPEG 换成 WebSocket 或 WebRTC，只要保留 Flask 对外接口或同步更新 `realtime.js`，不需要重写整个页面。

### OAK 设备排查

如果 C++ 报 `No available devices`，先查宿主机是否枚举到设备：

```bash
lsusb | rg -i '03e7|movidius|luxonis|depthai|oak'
```

如果没有输出，通常是：

- 设备没有接到当前系统。
- USB 线不是数据线。
- VM 没有做 USB 直通。
- OAK 供电不足。
- 设备还停留在宿主机，没有传进运行环境。

如果能看到设备但程序仍没有权限，再检查 udev 规则和重新插拔：

```bash
sudo udevadm control --reload-rules
sudo udevadm trigger
```

- MJPEG 会占带宽，第一版只推主画面是合理的。
- 状态数据不要塞进 MJPEG 帧里，继续走 `/status` JSON。
- 高频状态不建议轮询太快，1 秒一次足够显示页面指标；真正需要逐帧数据时再升级 WebSocket。

### 方案二：C++ 引擎 + Flask/WebSocket 桥接

这是计划文档里最推荐的正式架构方向。

改动思路：

```text
C++ 实时程序
  ├── 发布 frame/status 数据
  └── 接收 click/filter/control 命令

Flask
  ├── 接 C++ 数据
  ├── 用 WebSocket 推给浏览器
  └── 接浏览器命令再转给 C++

浏览器
  ├── WebSocket 收帧和状态
  └── WebSocket 或 HTTP 发控制
```

可以分两种做法：

第一种是 Flask 桥接：

- C++ 用 ZeroMQ、TCP 或本地 socket 发布数据。
- Flask 后台线程接收 C++ 数据。
- Flask-SocketIO 或原生 WebSocket 推给页面。
- 页面从 `<img>` 改为 `<canvas>`，收到 JPEG 二进制后画到 canvas。

第二种是 C++ 直接 WebSocket：

- C++ 增加 `/ws`。
- 浏览器直接连 `ws://127.0.0.1:8081/ws`。
- Flask 只负责页面。
- 需要解决跨域或仍由 Flask 做 WebSocket 代理。

建议演进路径：

1. 保留当前 HTTP 接口不删。
2. 新增 `/ws`，先只推状态 JSON。
3. 再推 JPEG 二进制帧。
4. 前端新增 canvas 渲染路径。
5. 确认稳定后再决定是否移除 MJPEG。

这样可以避免一次性重写实时页。

### 方案三：C++ 自建完整 HTTP/WebSocket 服务，Flask 只嵌入页面

当前已经实现了方案三的 HTTP 基础版。后续要让它更完整，需要把 C++ 服务从“附在 `get_pose_oak_rgbd.cpp` 上的 server mode”逐步拆成模块。

建议拆法：

```text
realtime/
  realtime_bridge.h/.cpp      HTTP/WebSocket 服务
  realtime_command.h          命令结构
  realtime_status.h           状态结构和 JSON 序列化
  realtime_frame_buffer.h     最新帧缓存
```

然后 `get_pose_oak_rgbd.cpp` 只保留主业务循环，不再堆太多 HTTP 细节。

如果做 WebSocket，C++ 服务应该统一输出：

```json
{"type": "status", "payload": {...}}
{"type": "frame", "encoding": "jpeg", "payload": "..."}
{"type": "landing", "payload": {...}}
```

也可以用二进制 WebSocket 帧传 JPEG，用 JSON 帧传状态。这样比把所有东西都塞 JSON base64 更高效。

### 方案四：pybind11 / 动态库嵌入 Flask

这个方案不建议作为近期方向，但如果以后要做，需要先把 C++ 主循环拆成类：

```cpp
class RealtimeEngine {
public:
  bool Start();
  void Stop();
  bool GetLatestFrame(std::vector<unsigned char>& jpeg);
  RealtimeStatus GetStatus();
  void PushCommand(const RealtimeCommand& command);
};
```

然后 pybind11 只绑定这个类，不要直接绑定散落在 `main` 里的全局变量。

风险点：

- Flask 进程崩溃会带着相机资源一起崩。
- Python GIL、线程生命周期、C++ 异常边界都要认真处理。
- Debug 难度比进程间 HTTP 更高。

如果要做，建议先完成 C++ 模块化，再封装 pybind11。

### 方案五：WebRTC / GStreamer

这个方向适合远程低延迟观看，不适合当前第一阶段。

改动思路：

- C++ 或 GStreamer pipeline 输出 H.264 / WebRTC 视频流。
- 状态、点击、滤波仍走 WebSocket 或 HTTP。
- 前端用 `<video>` 播放实时流，不再用 `<img>` MJPEG。
- 需要信令服务、编码器选择、网络穿透或局域网约束。

关键原则是：视频流可以换成 WebRTC，但控制协议不要和视频绑死。点击、滤波、状态仍应保持独立接口。

## 后续重构建议

当前实现为了快速跑通，把 `RealtimeBridge` 直接写在 `get_pose_oak_rgbd.cpp` 里。它可用，但不是长期最干净的结构。后续建议：

1. 把 `DepthUiState`、滤波 JSON 解析、状态 JSON 序列化移到独立头/源文件。
2. 把 `RealtimeBridge` 移到 `app/realtime_bridge.h/.cpp`。
3. 把键盘控制和 Web 控制统一成一个 `ApplyRealtimeCommand` 函数，减少重复分支。
4. 给 C++ 的 JSON 解析换成结构化 JSON 库，当前正则解析只适合简单数字字段。
5. 给 `/status` 增加错误状态和设备信息，例如 USB 状态、模型路径、服务启动时间。
6. 当前项目的 `AGENTS.md` 应补充实时服务运行命令和架构说明，因为这次已经新增了核心运行模式。
