# 蹦床标定回归与模块化：这次不是加功能，而是把已有能力锁稳

## 任务目标

这轮工作承接 2026-04-18 的关键帧标定补标实现，但目标不是继续加新能力，而是完成两件很关键的收尾工作：

1. **补齐自动回归测试**
2. **把前端标定逻辑从 `video_analysis.js` 中拆出来**

很多时候，功能已经“能跑”并不代表链路就稳定。真正可维护的工程，还要做到：

- 页面契约有保护
- API 返回 shape 有保护
- 复杂 UI 状态机不要继续堆在一个大文件里

## 为什么这轮工作很重要

如果没有这一步，后续风险会很高：

### 1. 页面和脚本可能慢慢脱节

比如：

- 模板改了一个 `id`
- JS 还在用旧 `id`
- 页面直接黑屏或者按钮失效

这种问题如果没自动化测试，往往只能靠人工点页面才发现。

### 2. 标定 UI 状态机太容易继续长歪

如果所有标定逻辑都还留在 `video_analysis.js` 里，随着功能继续增加，很容易出现：

- 状态变量互相污染
- 某个按钮职责不清
- 预览、草稿、关键帧列表耦合得越来越深

所以这次本质上是在做：

> **把现有可用能力“锁住”和“拆清楚”。**

## 这次具体改了什么

### 1. 自动回归测试补强

#### `tests/test_trampoline_frontend_contract.py`

新增/保留的重点是：

- JS `getElementById(...)` 与模板 `id="..."` 对齐检查
- trampoline 页面契约检查，确认页面包含：
  - pending calibration UI 节点
  - `trampoline_calibration_geometry.js`
  - `trampoline_calibration_ui.js`
  - `video_analysis.js`

这类测试不是在测“功能逻辑”，而是在测“接线关系有没有断”。

#### `tests/test_trampoline_api.py`

新增上传接口契约测试，确认 `/api/video/upload` 在 trampoline 模式下返回：

- `status=uploaded_pending_calibration`
- `first_frame_image`
- `first_frame_b64`
- `image_size`
- `video_fps`
- `total_frames`
- `corner_order`

这保证了前端上传后进入待标定态时，能拿到它必须依赖的数据。

#### `tests/test_trampoline_calibration_ui.mjs`

为拆出的前端标定模块增加纯函数级测试，验证：

- 按钮启用状态
- 草稿状态
- 状态文案

这说明测试不只是“点页面”，还在锁更小粒度的状态逻辑。

### 2. 前端标定逻辑模块化

#### 新增 `static/js/trampoline_calibration_ui.js`

这个模块现在专门负责 trampoline 待标定阶段的控制器逻辑，包括：

- 进入 pending calibration
- 草稿帧 / 首帧初始化
- 当前帧截图
- 床面四角点击与画布绘制
- calibration 列表、选中、高亮、删除
- 保存当前标定
- 提交 `/api/video/trampoline/start`

#### `static/js/video_analysis.js`

主文件不再继续塞满 trampoline 标定细节，而是改成：

- 在 trampoline 模式下初始化 `TrampolineCalibrationUI.createController(...)`
- 继续负责总流程：
  - 通用上传流程
  - 分析轮询
  - LLM / 报告 / 统计面板
  - 标定提交成功后启动分析轮询

#### `templates/video_analysis.html`

脚本加载顺序明确为：

1. `trampoline_calibration_geometry.js`
2. `trampoline_calibration_ui.js`
3. `video_analysis.js`

这类顺序约定很值得记下来，因为前端脚本经常会依赖前一个文件先把全局对象或函数准备好。

### 3. 样式清理

#### `static/css/video_analysis.css`

样式层做了两件事：

- 删除旧 trampoline keyframe UI 残留样式
- 保留当前 `.keyframe-row` 流程所需样式，并补充 `.keyframe-row.active` 高亮

这一步虽然看起来“小”，但它能减少旧样式和新逻辑互相打架的概率。

## 这些测试分别在锁什么

很多初学者会把“测试补齐”理解成多写几个断言，但更重要的是搞清楚：**每个测试到底在保护哪一层。**

### 页面契约测试

保护的是：

- 页面结构有没有把关键节点删掉
- 脚本接线有没有断

### API 契约测试

保护的是：

- 上传成功后，前端是否还能得到进入标定态所需字段

### UI helper / controller 测试

保护的是：

- 标定状态机内部逻辑有没有被改坏
- 按钮职责有没有混乱

这三类测试放在一起，才形成了真正有用的回归网。

## 这次能学到什么

### 1. 模块拆分很像把“驱动层”和“应用层”分开

如果你有 MCU C 背景，可以把这次拆分理解成：

- `trampoline_calibration_ui.js` 更像一个“专用子模块”或“驱动层控制器”
  - 只管标定状态机
- `video_analysis.js` 更像“应用层总流程”
  - 只管上传、轮询、报告、页面整体行为

如果这两层混在一起，后面一加功能就容易乱。

### 2. 前端也非常需要“接口契约”思维

在嵌入式里，大家很熟悉：

- 函数参数要固定
- 数据包结构要固定
- 模块边界要清楚

前端其实也是一样的，只不过这里的“接口”不只是函数，还有：

- 模板里的 `id`
- JS 里查 DOM 的方式
- 后端返回 JSON 的字段形状
- 脚本加载顺序

这就是为什么 `id` 对齐测试和 payload 契约测试很重要。

### 3. 这轮工作体现的是“先锁行为，再继续开发”

这次没有继续往页面上堆新按钮，而是先做了两件更稳的事：

- 用测试把已有行为锁住
- 用模块拆分把维护边界拉清楚

这是一种很值得学习的开发节奏。

## 后续优化

如果后面继续演进这条链路，建议优先遵守下面这套顺序：

1. 先在 `trampoline_calibration_ui.js` 内增量修改标定逻辑
2. 再同步更新对应契约测试
3. 最后再考虑是否需要继续拆分更细的 helper

这轮工作的核心价值，可以总结成一句话：

> 功能能跑只是开始，真正可维护的链路，要靠“回归测试 + 清晰边界”一起守住。
