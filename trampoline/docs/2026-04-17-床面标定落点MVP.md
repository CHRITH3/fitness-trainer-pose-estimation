# 床面标定落点 MVP：第一版可用链路说明

## 任务目标

这次工作的目标是：**在不重做现有跳次分割逻辑的前提下，为每次落地补上“落在床面的哪里”这条信息。**

换句话说，系统原来已经能回答“跳了几次、做了什么动作”，这次要让它继续回答：

- 落点坐标是多少
- 更接近床中心还是边缘
- 这次坐标是否可信

这里的关键词是 **MVP**。MVP 不是“随便先做一个”，而是“先打通最小可用链路”。所以这次不追求把所有漂移问题一次性解决，而是先把“上传 → 标定 → 分析 → 报告里看到落点”这条主链路真正跑通。

## 先理解原始问题

在没有床面标定之前，后端只能从人体关键点里判断跳跃事件，比如：

- 起跳
- 落地
- 动作分类

但是它并不知道“落地时脚在蹦床平面的哪个位置”。

这会带来两个实际问题：

1. **分析结果不够完整**
   - 只能知道动作和时间，不能知道是否偏床边、是否偏离中心。
2. **后续可视化和 AI 解读缺信息**
   - 没有床面坐标，就很难做落点分布图，也很难让 AI 对“稳定性”“控制力”做更细的解释。

同时，这里还有一个很重要的工程约束：

> **就算床面跟踪失败，也不能把原本已经可用的跳次分割主链路拖垮。**

所以这次设计不能把床面标定做成“主控制器”，而要做成一个**附加能力模块**。

## 为什么这次方案这样设计

这次没有把“落点定位”直接塞进 `TrampolineAnalyzer` 里，而是引入了一个单独的 `BedTracker`。这样设计有两个明显好处：

### 1. 责任更清楚

- `TrampolineAnalyzer` 继续负责：
  - 跳次分割
  - 动作识别
- `BedTracker` 只负责：
  - 根据人工四角标定和视频追踪，估计当前床面四边形
  - 把像素点映射到床面坐标

这样做的结果是：**床面坐标是附加信息，不是主流程依赖。**

### 2. 出错时更容易降级

如果 `BedTracker` 置信度不高，它可以：

- 继续输出低置信坐标
- 或者暂时不给出落点

但不应该影响“这是不是一次跳跃”这件事本身。

这是一种很典型的工程思路：

> 先把主流程保持稳定，再把增强信息作为可选层叠加上去。

## 整条链路是怎么打通的

可以把这次实现理解成下面这条流程：

1. 前端上传视频
2. 后端返回首帧图像
3. 用户在首帧上点击四个床角
4. 后端把四角写入 sidecar 文件
5. 子进程分析视频时逐帧更新 `BedTracker`
6. 当分析器识别出一次 `landing` 时，把落点信息挂到这次 jump 上
7. 报告、LLM、前端展示层继续消费这个增强后的结果

也就是说，这次没有发明第二套结果结构，而是选择在现有的 `completed_jumps[i]` 上增加一个可选字段 `landing`。

这个做法的优点是兼容成本低，因为旧结果结构并没有被推翻。

## 这次具体改了什么

### 1. `trampoline/bed_tracker.py`

这是这次新增的核心模块，主要负责：

- 接收首帧四角标定
- 校验角点顺序和合法性
- 用 LK 光流 + RANSAC 单应性逐帧更新床面四边形
- 把脚踝像素坐标映射成床面物理坐标、归一化坐标和区域分类
- 在低置信情况下仍输出结果，并把“不确定性”显式写进 `confidence` / `confidence_factors`

这里的关键不是“它会算坐标”，而是“它把坐标计算封装成独立职责”。

### 2. `video_processor.py`

视频子进程里新增了床面 sidecar 的读取与 `BedTracker` 更新逻辑：

- trampoline 模式读取 `<video_id>_corners.json`
- `BedTracker` 按**每个解码帧**更新
- `TrampolineAnalyzer` 仍按自己原有的采样节奏做跳次分析

这说明：

- 床面跟踪的时间粒度
- 跳次分析的时间粒度

可以不同步，但最终仍然可以在“落地事件发生时”拼起来。

### 3. `trampoline/analyzer.py`

分析器没有被改成“大一统模块”，而是只做了一件事：

- 在已有 `landing` 事件分支里，把 `completed_jumps[i].landing` 挂上去

这是一种非常值得学习的改法：

- 不推翻旧数据结构
- 只在最接近业务语义的地方补字段
- 失败时不破坏旧逻辑

### 4. `app.py`

上传流程改成了 trampoline 的两阶段流程：

1. `/api/video/upload`
   - 保存视频
   - 返回首帧 base64、图像尺寸、角点顺序
2. `/api/video/trampoline/start`
   - 校验角点
   - 写 sidecar
   - 启动子进程分析

这里的好处是：**人工标定和长时间视频分析被拆成两个明确阶段。**

### 5. 前端与报告层

前端新增首帧四角点击流程；报告层和 LLM 层开始在有 `landing` 时展示或解释落点信息。

这意味着这次改动不是只停留在后端算法层，而是把“数据从哪里来、怎么流到界面、怎么被解释”这整条链路补齐了。

## 关键数据结构应该怎么看

### 1. `completed_jumps[i].landing`

这是这次最重要的数据契约。它是**可选字段**，存在时结构大致如下：

```json
{
  "bed_xy_m": [2.0, 1.0],
  "norm_xy": [0.5, 0.5],
  "zone": "center",
  "dist_from_center_m": 0.0,
  "confidence": 0.67,
  "confidence_factors": {
    "tracking": 0.81,
    "ankle_visibility": 0.74,
    "bounds": 1.0
  },
  "ankle_px": [320.0, 240.0]
}
```

可以这样理解每个字段：

- `bed_xy_m`：物理坐标，单位是米，更接近“真实世界”
- `norm_xy`：归一化坐标，更适合前端画图
- `zone`：区域标签，便于做统计与解释
- `confidence`：整体可信度
- `confidence_factors`：把低置信的原因拆开，便于调试
- `ankle_px`：原始像素点，便于回查问题

### 2. sidecar 文件

角点 sidecar 文件形如 `<video_id>_corners.json`，schema version 为 `1`，角点顺序固定为：

```json
["front_left", "front_right", "back_right", "back_left"]
```

这个 sidecar 的本质，可以理解为：

> 视频本体不改，人工标定数据单独保存，供后续分析重复读取。

这样做比把标定信息硬塞进视频元数据更简单，也更容易调试。

## 失败模式为什么要单独讲

这类功能最怕的一种错误思路是：

- 床面跟踪失败
- 整个视频分析也跟着失败

这次实现刻意避免了这种耦合。设计上的要求是：

1. 映射失败不能影响原有跳次结果
2. 低置信结果可以继续输出，但要把“不确定”写清楚
3. 老结果没有 `landing` 时也要兼容

这说明系统做的是**增强型输出**，不是**单点致命依赖**。

## 这次能学到什么

### 1. 模块职责要像“传感器模块”一样拆

如果你有单片机 C 开发背景，可以把 `BedTracker` 理解成一个“给主流程补充测量值的传感器模块”：

- 它负责采集 / 估计自己的数据
- 它把结果交给主业务逻辑
- 但它不应该反过来控制主业务流程

在这次实现里，`TrampolineAnalyzer` 仍然是“跳次逻辑”的主人，`BedTracker` 只是“落点信息提供者”。

这和 MCU 里“主循环决定状态机，传感器驱动只提供测量值”的思路很像。

### 2. Python 里的“可选字段”是一种很实用的兼容方式

这次没有强迫每个 jump 都必须有 `landing`，而是让它成为可选字段。

这种写法的好处是：

- 老结果可以继续读
- 新能力可以逐步接入
- 前端和 LLM 可以按“有则展示，无则跳过”的方式升级

对 C 背景的人来说，可以把它想成“结构体里某个字段只有在特定功能启用时才有效”，只是 Python 通常用 dict 的存在/不存在来表达。

## 后续优化

这篇文档记录的是第一版可用链路，所以它天然还有后续空间：

1. **补做更强的漂移修正**
   - 例如 ORB / keyframe 方案
2. **加强前端引导**
   - 让“前左 / 前右 / 后右 / 后左”更容易理解
3. **继续校准置信度权重**
   - 用更多真实视频样本调参

如果把这次工作看成开发方法示例，那么最值得记住的一点是：

> 先把“主流程不受影响”的增强能力做通，再逐步提高它的精度和可解释性。
