# 标定漂移修复：先把坐标系讲清楚，再谈追踪稳定性

## 任务目标

这次修复要解决两个很典型的问题：

1. **前端点击坐标和真实视频像素坐标不一致**
   - 典型场景是竖屏、黑边、letterbox。
2. **长视频或手持视频里，床面四边形会逐渐漂移**
   - 即使一开始标得对，几跳以后也可能慢慢偏掉。

这两个问题看起来一个在前端、一个在后端，但本质上都和“坐标映射是否可信”有关。

## 先理解问题为什么会出现

### 1. 为什么点击位置会错位

浏览器里看到的视频矩形，不一定等于“真实视频像素区域”。

举个最常见的例子：

- 视频是竖屏
- 容器是横向区域
- 浏览器会做 `contain`
- 于是左右或上下会出现黑边

这时鼠标点到的 `clientX/clientY` 只是“显示区域坐标”，不一定落在真实视频内容里。

### 2. 为什么床面会漂移

后端床面跟踪依赖：

- LK 光流
- RANSAC 单应性

这些方法都很实用，但都可能在长时间累计中慢慢偏掉。尤其在下面这些场景里更明显：

- 手持镜头
- 可见特征少
- 人体遮挡床边
- 画面运动比较复杂

所以这次修复不能只做“算法更努力”，还要加“什么时候该怀疑算法”的判据。

## 为什么这次修复拆成前端和后端两条线

因为这两个问题虽然都表现为“点不准 / 框不准”，但根因不同：

- **前端问题**：坐标系算错了
- **后端问题**：追踪结果可能不再可信

如果把这两者混成一个补丁，很容易出现：

- 改完还是不清楚到底是谁的问题
- 后续排查越来越难

所以这次的工程思路是：

1. 先把坐标系映射做成纯函数
2. 再把跟踪可信度管理做成一组显式状态
3. 最后再增加 ORB/keyframe 重定位作为兜底

## 这次具体改了什么

### 1. 前端：统一使用内容区坐标映射

新增 `static/js/trampoline_calibration_geometry.js`，提供三个无依赖纯函数：

- `computeContainRect`
- `displayToImagePoint`
- `imageToDisplayPoint`

这里的设计重点是：**所有与标定点击相关的计算，都统一走同一套映射函数。**

这样可以避免：

- 绘制点时用一套逻辑
- 点击反算时又用另一套逻辑

这类“双重坐标逻辑”很容易在后期出 bug。

#### 结果

- 黑边点击不再生成角点
- 用户会被提示点击视频内容区域
- 角点仍以原始首帧图像像素坐标提交给后端

### 2. 后端：给 `BedTracker` 加上显式追踪状态

`BedTracker` 不再简单地“算得出来就更新”，而是增加了这些状态：

- `trusted`
- `low_confidence`
- `frozen`
- `tracking_lost`

这意味着系统开始区分：

- 当前结果是不是可信
- 是不是只能勉强参考
- 是不是该冻结上一个可信结果
- 是不是已经基本丢失跟踪

### 3. 加入 sanity gate，防止“越跟越偏”

LK/RANSAC 候选 homography 更新必须通过一组 sanity gate，例如：

- tracked points / inlier ratio
- 四边形凸性与自交检查
- 面积变化
- 中心位移
- 边长比例变化
- frame bounds 检查

这套机制的核心思想是：

> 不要因为“算法给了一个结果”，就默认它一定可信。

如果候选不可信：

- 不覆盖最后可信四边形
- 只降置信度
- 必要时进入 freeze / lost

### 4. 加入 ORB / keyframe 重定位作为兜底

这次还增加了基于 OpenCV ORB 的重定位：

- 初始化或可信更新时保存 keyframe 特征
- 当低置信或周期触发时，尝试 keyframe → current 的 ORB 匹配 + RANSAC 重定位
- 结果仍需通过同一套 sanity gate

注意这里的定位：

- ORB 不是主路径
- ORB 是“当正常追踪不稳时的兜底恢复路径”

### 5. Overlay 颜色也开始承担状态表达职责

Overlay 不只是“画个框”，而是让状态更容易被看懂：

- trusted：绿色
- low-confidence：黄色 / 橙色
- frozen / tracking-lost：灰色 / 红色标签

这说明可视化层也在参与“系统可解释性”。

## 坐标系应该怎么理解

这次修复里最值得学的一点，就是“显示坐标”和“图像坐标”不是一回事。

### 显示坐标

它来自浏览器当前页面布局，受这些因素影响：

- 视频容器大小
- CSS 布局
- letterbox 黑边
- 设备分辨率

### 图像坐标

它来自原始视频帧本身，比如：

- 1280 × 720
- 1920 × 1080

后端做床面映射、做 sidecar 存储时，需要的是图像坐标，而不是页面坐标。

所以 `displayToImagePoint()` 做的事，本质上就是：

> 先找到真实视频内容区，再把用户点击换算回原始像素坐标。

## 这次能学到什么

### 1. `computeContainRect()` 的思想很像“有效数据区”判断

如果你有 MCU 背景，可以把 `computeContainRect()` 理解成：

- 先算出“真实有效的数据区”
- 缓冲区外的区域虽然显示出来了，但不代表可以采样

这和很多嵌入式场景很像：

- DMA 缓冲区大小是固定的
- 但真正有效的数据长度可能更小
- 你不能把无效区域也当成数据来处理

在这里，黑边就像“显示出来但并不属于真实视频内容的区域”。

### 2. 追踪状态机比“单一成功/失败标志”更实用

很多初学者会把追踪结果理解成：

- 成功
- 失败

但真实系统更常见的是中间态：

- 还能用，但不太稳
- 暂时冻结更安全
- 基本丢失，需要兜底恢复

所以 `trusted / low_confidence / frozen / tracking_lost` 这种状态设计，比一个简单 `bool ok` 更有工程价值。

### 3. sanity gate 是“算法结果的二次审核”

算法不是法官，算法只是候选生成器。

真正稳的系统，会在算法输出之后再加一层工程判据，检查：

- 合不合理
- 会不会突然跳变
- 是否越界
- 是否破坏几何关系

这类设计在 Web / Python 后端里很常见，本质上和 MCU 里“采样值出来后先过阈值/滤波/合法性检查”是同一类思路。
