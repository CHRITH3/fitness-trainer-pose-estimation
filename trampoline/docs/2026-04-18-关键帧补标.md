# 关键帧补标实现与复核记录：从功能接线到回归闭环

## 这篇文档的定位

这篇文档记录的是“关键帧补标”这轮工作的**实现落地 + 复核过程**。

它和纯方案文档的区别在于：

- 不只讲设计目标
- 还要讲当时代码是怎么接线的
- 哪些验证已经通过
- 哪些问题是在复核阶段暴露出来、后来又怎么修掉的

这种文档很适合学习真实开发过程，因为真实项目往往不是“一次提交就稳定”，而是：

1. 先把需求接上
2. 再靠测试和复核把问题压出来
3. 最后把状态收敛到真正可交付

## 任务目标

本轮工作对应：

- `.omx/plans/ralplan-trampoline-keyframe-line-minimap.md`
- `.omx/plans/prd-trampoline-keyframe-line-minimap.md`
- `.omx/plans/test-spec-trampoline-keyframe-line-minimap.md`

目标是在 trampoline 上传分析流程中补齐三件事：

1. **分析前多关键帧床面补标**
2. **marker line 最佳努力高亮**
3. **右下角落点 minimap 自适应缩放**

## 先从用户视角理解这条链路

从使用者角度看，这条链路大致是：

1. 上传视频
2. 预览视频
3. 暂停到某一帧
4. 点击“添加当前帧标定”
5. 在该帧上补四个角点
6. 保存成一个关键帧
7. 可以继续添加第二个、第三个关键帧
8. 提交到 `/api/video/trampoline/start`

也就是说，这次新增能力不是后台自动猜出来的，而是允许用户在分析前提供多组**按时间组织的人类锚点**。

## 为什么这轮工作不能只看“功能有没有出现”

关键帧补标这类功能，最容易出现一种误判：

- 页面上已经能看到按钮
- 接口也能收 `calibrations[]`
- 所以任务应该已经完成了

但工程里真正重要的是：

- 结构是不是接对了
- 兼容路径是不是稳的
- `BedTracker` 在读这些关键帧时会不会引入回归

所以这轮文档除了记录“接上了什么”，还会记录“复核时曾暴露过什么问题”。

## 这次已经落到代码里的实现

### 1. API / sidecar 已支持多关键帧

#### `app.py`

在当前代码里，关键帧相关的规范化和提交流程主要体现在：

- `validate_calibrations(...)`
- `_calibrations_equal(...)`
- `_normalize_trampoline_calibrations(...)`
- `/api/video/trampoline/start`

也就是说，start 接口现在已经能同时处理：

- 新格式 `calibrations[]`
- 旧格式 `corners`

而且旧格式会被自动归一化为 frame 0 的单关键帧记录。

这种写法很重要，因为它把兼容逻辑集中在“输入归一化”这一步，而不是让后续业务逻辑分支到处判断“到底是旧格式还是新格式”。

#### sidecar 写入字段

sidecar 中现在能表达的关键信息包括：

- `frame_index`
- `time_s`
- `corners_px`
- `calibrations`

这意味着 sidecar 已经从“只存首帧四角”升级成“按时间组织的一组人工锚点”。

## start 请求的数据应该怎么理解

这轮工作的核心协议变化，是把 start 请求从“只交一组 corners”升级为“交一个 calibrations 数组”。

可以把它理解成下面这种结构：

```json
{
  "video_id": "...",
  "calibrations": [
    {
      "frame_index": 0,
      "time_s": 0.0,
      "corners_px": [
        {"name": "front_left", "x": 10, "y": 20}
      ]
    }
  ]
}
```

如果还是旧格式 `corners`，后端会自动把它归一化成 frame 0 的单关键帧。

这是一种很值得学习的 API 设计方式：

> 外部协议可以升级，但内部处理尽量统一成一种标准形状。

## 这次能学到什么

### 1. `captureCurrentVideoFrame()` 很像“锁存当前采样值”

前端不是直接在持续播放的视频流上编辑关键帧，而是先把当前帧抓出来，再让用户补角点。

如果你有 MCU 背景，可以把这个动作理解成：

- 先把当前采样值锁存到缓冲区
- 再基于这个稳定快照去修改和计算

这样做的好处是：

- 当前编辑对象是稳定的
- 不会边播边改，导致状态漂移

### 2. `calibrations[]` 本质上是一组“按时间组织的快照”

关键帧不是实时状态，而是一组按 `frame_index` 保存的静态记录。

这和嵌入式里“存多个校准点，再按条件选择哪个校准点生效”的思路很像。

### 3. 档案型文档也要区分“历史问题”和“当前事实”

这篇文档最值得学习的一个写法点是：

- 可以记录某个问题在 review 阶段出现过
- 但必须明确它属于“当时的问题”，还是“当前仍未解决的问题”

否则文档会把后续维护者带偏。
