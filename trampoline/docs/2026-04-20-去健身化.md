# 2026-04-20 去健身化执行说明

> 这是一篇**内部档案型文档**。
>
> 它保留这次整理任务的历史背景，但目的不是对外讲项目来历，而是帮助后续维护者理解：为什么要做这轮收敛、怎么做才安全、哪些旧内容值得学习、哪些内容应该果断删除。

## 任务目标

这轮整理的核心目标是：**把仓库收敛成“蹦床单产品语义”的代码库，同时保留已有蹦床分析能力与稳定公共路由。**

当时需要保留的入口包括：

- `/`
- `/dashboard`
- `/profile`
- `/video_analysis`

这里最容易做错的一件事，是把“删除旧能力”理解成“把所有旧结构都一起砍掉”。

但实际工程里，正确目标是：

- 删掉不再服务当前产品方向的实现
- 保留仍有价值的页面壳层、路由与流程骨架
- 让仓库最终读起来、跑起来都围绕蹦床主线

## 为什么这轮整理很有必要

如果仓库长期保持“多套旧语义并存”，会产生几个明显问题：

1. **读代码的人会混淆当前主线**
   - 不清楚哪个流程还在用，哪个流程只是遗留。
2. **前后端会长期背着无效语义负担**
   - 页面、接口、文案和模块名都会越来越难理解。
3. **后续扩展蹦床能力时，容易在旧结构上继续缝缝补补**
   - 结果就是目录越来越乱，判断成本越来越高。

所以这轮整理的本质不是“做文案替换”，而是：

> **把仓库重新整理成一个对当前目标负责的系统。**

## 这次采用的策略

这次没有直接粗暴删除所有旧内容，而是采用了更安全的顺序：

1. 先明确蹦床当前必须保留的公共路由与主链路
2. 再把后端与前端收敛到 trampoline-only 语义
3. 最后删除不再需要的旧模块、旧接口与旧语义说明

这样做的好处是：

- 主链路不容易被误伤
- 页面入口保持稳定
- 用户与维护者都更容易理解当前仓库边界

这说明“页面保留”不等于“旧功能保留”。真正被保留的是：

- 页面路由
- 页面骨架
- 后续扩展入口

文档层也做了同步整理：

- **被保留的是仍然对蹦床产品有价值的工程骨架**

## 从被删除内容中提炼出的可复用思路

### 1. 页面骨架复用

虽然旧页面语义不再保留，但 dashboard / profile 的卡片布局、图表容器和双栏结构，仍然适合后续蹦床项目使用。

这说明删除旧业务时，不要只看“它以前叫什么”，还要看“它的结构有没有继续利用价值”。

### 2. 上传 + 状态轮询链路

视频分析页原来就已经具备：

- 上传
- 后端处理
- 轮询状态
- 展示报告

这条链路本身是健康的，所以更合理的做法不是全部推倒重来，而是把它保留为蹦床主链路基础。

### 3. 配置与分层意识

即使是旧业务，前后端、分析引擎、页面模板、报告逻辑的分层方式仍然有学习价值。

工程里常见的一个误区是：

- 既然旧产品方向不用了
- 那旧代码就“一无是处”

实际上，很多时候真正有价值的不是旧业务名词，而是它背后的分层方法。

### 4. 报告 / AI 解释层

AI 分析的分段展示卡片、流式返回、缓存思路，也可以继续作为蹦床分析解释层基础。

## 这次能学到什么

### 1. 路由稳定性本身也是一种产品资产

这次没有把 `/dashboard`、`/profile` 这些入口全部砍掉，而是保留为壳层页面。

这很像固件里删掉一整套旧命令，但保留底层通信层和设备编号：

- 对外入口保持稳定
- 内部功能语义换成新的主线

这是一种很实用的“渐进式收敛”方式。

### 2. `upload_video()` 只接受 `exercise_type='trampoline'` 的意义

这里值得学的不是“参数换了个值”，而是：

- 系统边界终于被明确表达出来
- 无效分支不再继续存在于主路径里

对 MCU 背景的人来说，可以把它理解成：

- 通信协议层还在
- 但只保留当前有效的命令集
- 无用命令字和对应处理逻辑被清理掉

### 3. 真正的整理，不是单纯删除文件

工程里的整理更像三步：

1. 确定当前主线是什么
2. 确定哪些结构还能复用
3. 再决定哪些旧内容应该删除

如果顺序反过来，往往会删得很爽，但后面补得很痛苦。

## 验证

- 蹦床主链路是否仍然可用
- 公共路由是否仍然稳定
- 文案与页面是否已经收敛到当前产品方向

因此当时的重点验证思路包括：

- README 与页面是否按蹦床语义呈现
- `/`、`/dashboard`、`/profile`、`/video_analysis` 是否仍可访问
- `/api/video/upload` 是否明确只接受 trampoline 上传
- 蹦床视频分析主链路是否仍然可跑
